# Qwen3.5 GDN 对 D-Cut 变长验证的适配分析

## 1. 文档目的

本文说明 vLLM Ascend 0.23.0 中，Qwen3.5 的 Gated DeltaNet（GDN）为了支持
D-Cut 自适应验证长度所做的适配。

本文讨论当前默认安全路径，以及可选的 GDN PIECEWISE 真正入图路径：

- 默认 `VLLM_ASCEND_ENABLE_DCUT_GDN_PIECEWISE=0`，保留
  `torch.ops.vllm.qwen_gdn_attention_core` splitting boundary，GDN eager 执行；
- 设置开关为 `1` 后，只移除这个 GDN splitting boundary；
- 只有纯 speculative decode、PCP=1、DCP=1 且启动时已经捕获的 token bucket
  会 replay GDN PIECEWISE 图；
- prefill、普通 decode、混合 batch、缺少 GDN metadata、未捕获 bucket 和
  PCP/DCP 并行都会 fail-closed 回退到 eager；
- full attention 仍保留为 PIECEWISE eager boundary；
- D-Cut 始终只替换 GDN `_forward_core`，不替换模型和算子实现。

因此，“GDN 入图”在本文中特指上述受控的纯 speculative decode 路径，并不表示
所有 GDN 阶段都进入 ACL Graph。

## 2. 一句话总结

GDN 适配 D-Cut 的核心是：

> 将“上一轮接受到的状态位置”与“本轮实际保留的验证长度”解耦，使每个请求即使
> 本轮只验证少量 token，仍能正确读取上一轮接受位置对应的 Conv1D 和 recurrent
> state，并只更新本轮真实存在的 token 槽位。

整体调用链如下：

```text
Drafter 生成固定上限的候选 token
        |
        v
D-Cut Controller 为每个请求计算本轮验证长度
        |
        v
截短 scheduler_output.scheduled_spec_decode_tokens
        |
        v
vLLM Ascend 原生 GDN metadata builder
        |
        v
torch.ops.vllm.qwen_gdn_attention_core
（开关 0：splitting op/eager；开关 1 且满足安全条件：进入 PIECEWISE 图）
        |
        v
D-Cut 替换后的 GDN _forward_core
        |
        +--> npu_dcut_causal_conv1d
        |
        +--> npu_dcut_recurrent_gated_delta_rule
```

## 3. 为什么原生 GDN 不能直接适配 D-Cut

### 3.1 D-Cut 会让每个请求的验证长度不同

普通 parallel speculative decoding 通常为 batch 内请求安排固定上限的 draft
token。D-Cut 会根据 drafter 置信度和硬件 cost profile，为每个请求单独选择本轮
验证长度。

例如：

```text
request A: 原始 draft 长度 8，D-Cut 保留 2
request B: 原始 draft 长度 8，D-Cut 保留 5
request C: 原始 draft 长度 8，D-Cut 保留 8
```

`dcut/truncate.py` 会同时更新：

- `scheduled_spec_decode_tokens`
- `num_scheduled_tokens`
- `total_num_scheduled_tokens`

这样后续 model runner 和 attention metadata builder 看到的就是实际裁剪后的变长
batch，而不是固定 speculative 长度。

对应实现：

- [`truncate.py`](truncate.py)
- [`patch_runner.py`](patch_runner.py)

### 3.2 GDN 有两类跨轮次状态

Qwen3.5 GDN 至少需要维护两类状态：

1. Conv1D 滑动窗口状态，即 `kv_cache[0]`；
2. recurrent/SSM 状态，即 `kv_cache[1]`。

这两类状态都需要从上一轮真正接受的位置继续计算。

问题在于：

```text
上一轮接受位置 = 6
本轮 D-Cut 验证长度 = 2
```

上一轮状态位置可能大于本轮 token 段长度。如果仍使用“本轮长度”推导上一轮状态
位置，会出现：

- 读取错误的 Conv1D 窗口；
- recurrent state 选择错误；
- 将 padding 槽位当成有效状态；
- `num_accepted_tokens` 大于本轮 varlen segment，导致算子参数校验失败；
- 不同请求的状态发生错位或串扰。

因此，不能简单地给 D-Cut 设置一个 GDN 最小长度来规避问题。正确做法是让算子
独立接收：

- 本轮真实 token 边界；
- 上一轮接受位置；
- 请求对应的状态槽位。

## 4. Scheduler 层：按请求裁剪验证 token

`NPUModelRunner.execute_model()` 在进入原生执行路径之前调用 `_dcut_truncate()`。

核心逻辑为：

```python
target_len = min(max(adaptive_len, 0), max_draft_len)
new_spec[req_id] = draft_tokens[:target_len]
new_num_scheduled[req_id] -= max_draft_len - target_len
```

如果目标长度为 0，则该请求会从本轮的
`scheduled_spec_decode_tokens` 中移除，避免空 entry 仍被识别成 speculative
请求。

这一步只负责改变 scheduler 输出，不直接操作 GDN cache。新的请求长度随后由
vLLM Ascend 原生 metadata builder 转换为：

- speculative token 索引；
- non-spec token 索引；
- `query_start_loc`；
- Conv cache 索引；
- SSM state 索引；
- `num_accepted_tokens`。

## 5. Patch 安装与 GDN 入图开关

`dcut/install.py` 始终选择 `patch_gdn_v023.py`，不再根据入图开关切换到旧的
`patch_gdn.py`。这样 eager 和 graph 路径共用同一套 vLLM 0.23 GDN 状态语义。

`patch_gdn_v023.py` 完成三件事：

1. 检查两个 D-Cut Torch op 是否已经注册；
2. 必要时加载 `dcut_torch_ops.so`；
3. 将 Qwen3.5 GDN 类的 `_forward_core` 替换为
   `gdn_forward_v023.py` 中的实现。

Patch 同时更新：

```python
ascend_gdn.AscendGatedDeltaNetAttention._forward_core
target_class._forward_core
```

这里有意不替换整个模型，也不改变 GDN 对外的 `forward`。

因此原有调用仍然是：

```python
torch.ops.vllm.qwen_gdn_attention_core(
    mixed_qkv,
    b,
    a,
    core_attn_out,
    self.prefix,
    False,
)
```

变化发生在该 custom op 后面真正执行 GDN core 的 Python/NPU 实现，以及开启
入图时的 splitting boundary 和 graph replay 元数据路由。

### 5.1 真正入图的关键约束

`patch_piecewise.py` 在配置创建阶段读取集中注册的
`VLLM_ASCEND_ENABLE_DCUT_GDN_PIECEWISE`。只有同时设置 D-Cut 配置且该开关为
`1` 时，它才从
`splitting_ops` 中移除 `vllm::qwen_gdn_attention_core`；full attention 仍由
`patch_attention.py` 保持 eager boundary。

`gdn_buffers.py` 为每个 model instance、GDN layer prefix 和 padded token bucket
分配固定地址的：

- `qsl`：补齐后的 speculative `query_start_loc`；
- `ssi`：按请求保留二维结构的 state indices；
- `nat`：被本轮 segment 长度 clamp 后的 accepted token 数；
- `asl`：固定容量的 actual sequence lengths；
- `token_mask`：屏蔽 padded token 的输出。

启动真实 warmup 时，runner 强制构造纯 speculative GDN dummy metadata，为所有
配置的 PIECEWISE token bucket 预捕获图。每次 replay 前只刷新上述固定地址缓冲的
内容，不替换 tensor 地址。

运行时必须同时满足以下条件才允许 replay：

1. batch 中存在 GDN metadata；
2. `spec_sequence_masks` 存在且 `num_spec_decodes > 0`；
3. `num_prefills == 0` 且 `num_decodes == 0`；
4. state indices 是二维且不超过 `max_num_seqs`；
5. token bucket 已在启动阶段捕获；
6. PCP=1 且 DCP=1。

任一条件不满足，runner 会临时把本批的 `cudagraph_runtime_mode` 改为
`CUDAGraphMode.NONE`，执行完 eager forward 后再恢复；不会在准备失败后继续 replay。
TP>1 不在此处禁用，但依赖 D-Cut 的 TP decision 广播保证各 rank 选择相同长度。
捕获阶段还通过 `torch.npu.is_current_stream_capturing()` 断言 GDN 确实位于活动的
ACLGraph stream 内，而不是仅从配置上推断“已经入图”。

对应实现：

- [`install.py`](install.py)

- [`patch_attention.py`](patch_attention.py)
- [`patch_runner.py`](patch_runner.py)
- [`gdn_buffers.py`](gdn_buffers.py)

## 6. GDN core 中的 batch 拆分

替换后的 `_forward_core` 继续使用原生 `GDNAttentionMetadata`。

首先根据 metadata 取出：

```text
spec_sequence_masks
spec_token_indx
non_spec_token_indx
spec_state_indices_tensor
non_spec_state_indices_tensor
num_actual_tokens
```

随后按 batch 类型拆分输入：

### 6.1 纯 speculative batch

当不存在 prefill 和普通 decode 请求时：

```python
mixed_qkv_spec = mixed_qkv
mixed_qkv_non_spec = None
```

不需要额外的 gather。

### 6.2 speculative 与其他请求混合

使用 metadata 给出的索引分别取出：

```python
mixed_qkv_spec = mixed_qkv.index_select(0, spec_token_indx)
mixed_qkv_non_spec = mixed_qkv.index_select(0, non_spec_token_indx)
```

GDN gating 输出 `g` 和 `beta` 也按相同方式拆分。

### 6.3 没有 speculative 请求

不使用 D-Cut 算子，全部进入原生 non-spec 路径。

## 7. D-Cut Conv1D 状态算子

### 7.1 输入语义

`npu_dcut_causal_conv1d` 的关键输入如下：

| 输入 | 作用 |
| --- | --- |
| `query_start_loc` | 描述本轮每个请求实际拥有的 token 区间 |
| `cache_indices` | 每个请求对应的 Conv1D cache 行 |
| `state_offsets` | 每个请求应该从上一轮哪个接受位置读取历史窗口 |
| `conv_state` | GDN 的 Conv1D 滑动窗口状态 |
| `x` | 本轮经过投影的 speculative token |

`state_offsets` 在 device 上计算：

```python
state_offsets = num_accepted_tokens[:num_requests].to(torch.int32) - 1
state_offsets = state_offsets.clamp_min(0).contiguous()
```

这里没有对 NPU tensor 调用 `.item()`，避免在逐请求热路径引入 CPU-NPU 同步。

### 7.2 为什么需要独立的 `state_offsets`

原生路径容易把上一轮状态位置和本轮 varlen token 段绑定在一起。D-Cut 路径把二者
拆开：

```text
query_start_loc  -> 本轮要算多少 token
state_offsets    -> 上一轮从哪个位置继续
cache_indices    -> 状态属于哪个请求
```

因此，即使：

```text
上一轮接受 6 个 token
本轮只验证 2 个 token
```

算子仍可以从上一轮第 6 个位置对应的窗口继续，同时只处理本轮两个 token。

### 7.3 状态写回

算子只更新本轮真实 token 对应的 Conv1D 状态，不应让 padding token 改写有效请求
的历史窗口。无效槽位使用：

```python
DCUT_PAD_SLOT_ID = -1
```

调用位置：

- [`gdn_forward_v023.py`](gdn_forward_v023.py)
- [`dcut_causal_conv1d`](kernel/dcut_causal_conv1d/)

## 8. D-Cut recurrent GDN 状态算子

### 8.1 输入语义

`npu_dcut_recurrent_gated_delta_rule` 的关键输入如下：

| 输入 | 作用 |
| --- | --- |
| `actual_seq_lengths` | 本轮各请求的真实 token 长度 |
| `ssm_state_indices[B, S]` | 每个请求、每个 speculative 位置对应的 SSM 状态槽位 |
| `num_accepted_tokens[B]` | 上一轮各请求真正接受的 token 数 |
| `state` | recurrent/SSM 状态缓存 |
| `query/key/value/g/beta` | 本轮 GDN recurrent 计算输入 |

与原生路径直接 flatten 状态索引不同，D-Cut 算子保留
`ssm_state_indices[B, S]` 的请求维度。

这样算子可以按 request 行完成：

1. 根据 `num_accepted_tokens` 找到上一轮最后接受位置；
2. 从该位置对应的 SSM 槽位读取 initial recurrent state；
3. 只计算本轮 `actual_seq_lengths` 指定的有效 token；
4. 只写回本轮有效 token 对应的状态槽位。

### 8.2 解决的问题

该设计避免：

- 固定读取每行最后一个 speculative 槽位；
- 把 padding 槽位当作有效 recurrent state；
- 因不同请求长度不同而 flatten 后错位；
- 上一轮接受位置大于本轮长度时发生越界或状态回退；
- 为 GDN 强制增加 D-Cut 最小验证长度。

调用位置：

- [`gdn_forward_v023.py`](gdn_forward_v023.py)
- [`dcut_recurrent_gated_delta_rule`](kernel/dcut_recurrent_gated_delta_rule/)

## 9. Speculative 与 non-spec 分支边界

当前适配刻意限制在 speculative decode 分支。

| 场景 | Conv1D 路径 | Recurrent 路径 |
| --- | --- | --- |
| Speculative decode | `npu_dcut_causal_conv1d` | `npu_dcut_recurrent_gated_delta_rule` |
| 普通 decode | 原生 `npu_causal_conv1d_custom` | 原生 `npu_recurrent_gated_delta_rule` |
| Prefill | 原生 Conv1D/prefill 实现 | 原生 `chunk_gated_delta_rule` |
| Mixed batch | spec 部分用 D-Cut，其他部分用原生路径 | 分别计算后再合并 |

对于 mixed batch，最终使用原来的 token 索引将输出写回：

```python
merged_out.index_copy_(1, spec_token_indx, core_attn_out_spec)
merged_out.index_copy_(1, non_spec_token_indx, core_attn_out_non_spec)
```

这保证输出顺序与 scheduler/model runner 的原始 token 排列一致。

## 10. Torch schema、NPU 实现与 Meta 实现

两个 D-Cut 算子通过 `_C_ascend` namespace 注册：

```text
npu_dcut_causal_conv1d
npu_dcut_recurrent_gated_delta_rule
```

注册分为三部分：

1. `TORCH_LIBRARY_FRAGMENT`：声明 Torch schema；
2. `PrivateUse1`：绑定真实 NPU 实现；
3. `Meta`：描述输出 shape、dtype 和 alias 关系。

其中 schema 显式标记了可变状态：

```text
Tensor(a!) state
Tensor(b!) conv_state
```

这使 PyTorch 能识别算子对状态 tensor 的原地副作用。Meta 实现本身只解决
shape/alias 分析问题，不能单独证明 GDN 已经进入 ACL Graph。

对应代码：

- [`dcut_torch_binding.cpp`](kernel/torch_extension/dcut_torch_binding.cpp)
- [`dcut_causal_conv1d_torch_adpt.h`](kernel/dcut_causal_conv1d/dcut_causal_conv1d_torch_adpt.h)
- [`dcut_recurrent_gated_delta_rule_torch_adpt.h`](kernel/dcut_recurrent_gated_delta_rule/dcut_recurrent_gated_delta_rule_torch_adpt.h)

## 12. 适配范围和非目标

### 已适配

- DFlash/PARD 等 parallel speculative method；
- 每个请求不同的 D-Cut 验证长度；
- 上一轮接受位置大于本轮验证长度；
- Conv1D 状态独立寻址；
- recurrent/SSM 状态独立寻址；
- mixed speculative/non-spec batch 的 eager 正确性；
- 纯 speculative decode 的受控 PIECEWISE GDN 入图；
- 未满足安全条件时的 eager 回退；
- A2/A3 对应的独立 AscendC 构建路径。

### 尚未纳入 GDN 图 replay

- prefill、普通 decode 和 mixed speculative/non-spec batch；
- PCP>1 或 DCP>1；
- 启动阶段没有成功捕获的 token bucket；
- 310P D-Cut 变长 GDN；当前代码明确拒绝该路径。

Meta schema 只能提供 shape/alias 信息，不能替代固定地址刷新、阶段隔离和真实
ACLGraph stream 断言；dummy 权重或仅启动成功也不能替代真实权重精度与稳定性验证。

## 15. 最终结论

Qwen3.5 GDN 真正入图的前提仍然是先保证 D-Cut 状态语义正确。

原生 GDN 将 speculative token 位置、上一轮接受位置和状态槽位紧密关联。D-Cut
引入按请求、按轮次变化的验证长度后，这种关联不再成立。

当前适配通过两个 state-aware AscendC 算子，将三件事明确分开：

```text
本轮计算长度     -> query_start_loc / actual_seq_lengths
上一轮接受位置   -> state_offsets / num_accepted_tokens
请求状态槽位     -> cache_indices / ssm_state_indices
```

因此 GDN 可以在不设置人为最小验证长度的情况下支持 D-Cut 变长 speculative
verification；开启入图开关后，纯 speculative decode 使用固定地址元数据安全 replay
